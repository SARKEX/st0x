## What's NOT done yet (next session priorities)

### 1. `makerOrders.ts:240` — ioRatio extraction is `'0x'` placeholder

The fixed-limit Rainlang stores the ratio inside `evaluable.bytecode` — it's not
a top-level OrderV4 field. The on-chain `quote()` call resolves the ratio at
runtime by interpreting the bytecode. Until we surface a real `ioRatio` to the
ApiOrderSummary, the UI's `convertApiOrderToProcessedQuote` may drop our maker
order from walkOrderbook because `parseFloat('0x')` is NaN.

**Two options:**
- (a) Call the orderbook's `quote()` directly from the helper (eth_call against
  anvil) after deploy, capture the hex Float ratio, store it in
  `DeployedMakerOrder.ioRatio`. Most accurate. Needs the quote function
  selector + ABI from the Rain orderbook contract.
- (b) Compute the hex-Float from the user-provided `pricePaymentPerAsset` via
  `Float.parse(...).asHex()` (from `@rainlanguage/float`). Faster but doesn't
  exercise the on-chain interpreter path.

(a) is the production-faithful answer; (b) is fine for a smoke test.

### 2. Test rewrite (`marketBuy.spec.ts` + `marketSell.spec.ts`)

Pattern:

import { deployMakerLimitOrder } from '../../helpers/makerOrders';

    holder: MAKER_ACCOUNT.address, amount: parseUnits('5', 18) });

  // 2. Maker deploys SELL limit @ $300/wtCOIN, 1 wtCOIN depth

    testClient,
    makerPrivateKey: MAKER_ACCOUNT.privateKey,
    assetToken: { ...tokens.wtCOIN, symbol: 'wtCOIN' },
    paymentToken: { ...tokens.USDC, symbol: 'USDC' },
    side: 'sell',
    pricePaymentPerAsset: '300',
    depositAmount: parseUnits('1', 18) // 1 wtCOIN
  });
  registerMakerOrders(makerOrder);

  // 3. Fund taker with USDC

    holder: fundedAccount.address, amount: parseUnits('500', 6),
    balanceSlot: tokens.USDC.balanceSlot });

  // 4. Drive UI as taker: spend $300 → expect ~1 wtCOIN received
  await page.goto(`${process.env.PREVIEW_URL}/trade/${tokens.wtCOIN.id}`);
  // ... open trade, market buy, submit
  // 5. Assert wtCOIN balance went up by ~1, USDC balance went down by ~300

## Open questions

1. **`addOrder3` selector** — `makerOrders.ts:46-49` hardcodes the ABI shape.
   The deployed Rain orderbook is a custom build (per 2026-05-18 handover); the
   selector should match. If `decodeFunctionData` throws "selector mismatch",
   we'll need to inspect the bare calldata's first 4 bytes and adjust. Likely
   correct because LimitOrder.svelte uses the same SDK path.

2. **Vault initialization** — synthetic SgOrder reports balance `0x0`. After
   the maker deploys with a deposit, the orderbook contract has the funds but
   the synthetic SgVault still says zero. The SDK's preflight reads vault
   balance via `quote()` on anvil (not from sgOrder.balance), so this is
   probably fine. If walkOrderbook calls anything that reads
   `sgOrder.outputs[i].balance` directly, we'd need to inject the real balance.
   Worth verifying in the first test run.

3. **Multiple maker orders per test** — `registerMakerOrders` accepts a
   variadic list. Untested. The Goldsky filter handles arrays
   (`orderHash_in`), but the REST stub's pagination is hardcoded
   (`totalPages: 1`). Fine for `≤ pageSize` orders; revisit if tests need more.
