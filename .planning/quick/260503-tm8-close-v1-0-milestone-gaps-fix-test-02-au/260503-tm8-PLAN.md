`AuditEventType` (line 10–36) is a closed string-literal union. Currently includes `ACCESS_CODE_CREATED`, `ACCESS_CODE_DELETED`, `ACCESS_CODE_UPDATED`, `REFERRAL_CACHE_REFRESH`, plus paired `_FAILED` variants for some events (`ADMIN_LOGIN_FAILED`, `REFERRAL_UPDATE_FAILED`, `REFERRAL_MIGRATION_FAILED`). It does NOT yet include failure variants for ACCESS_CODE_* or REFERRAL_CACHE_REFRESH.

**Pattern observed in existing logFailure call sites** (`src/routes/api/admin/snapshots/trigger/+server.ts:191–197` is the canonical exemplar):

```typescript
} catch (error) {
    console.error('[Manual Trigger] Error generating snapshots:', error);
    try {
        await audit.logFailure(
            'SNAPSHOT_TRIGGERED',          // ← reuses the success event type; the success:false flag distinguishes
            { date: dateForAudit, ... },
            error instanceof Error ? error.message : 'Unknown error',
            { adminUser: 'admin' }
        );
    } catch (auditErr) {
        console.error('[...] Audit-log failure emission failed:', auditErr);
    }
    return json({ success: false, error: ... }, { status: 500 });
}
```

Key invariants from this pattern:
- Reuse the same event-type string as the success path (e.g. `ACCESS_CODE_CREATED` not `ACCESS_CODE_CREATE_FAILED`); the `success: false` field already disambiguates. Do NOT extend `AuditEventType` unless an existing paired `*_FAILED` literal is the established convention for that endpoint.
- Wrap the audit call in its own try/catch so an audit outage never converts a 4xx/5xx response into a 500.
- Pass the actor as `{ adminUser: 'admin' }` (matches `logSuccess` calls in same file).
- Do NOT change the existing 4xx/5xx response shape; the audit log is additive.

`createAuditLogger(request)` is already invoked at the top of each affected handler — no new instantiation needed.
